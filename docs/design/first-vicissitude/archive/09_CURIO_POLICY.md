# 09 — Curio 免没收与返还

免没收标签是确定需求。D6 已由用户选定：**自动返还＋凭证兜底**，理由是满背包不能导致吞物品。
本页下方「推荐默认」即选定实现，凭证作为兜底保留；「凭证备选」段落记录原始比较，不再是未决选项。
实际实现与未验证项见 [11 验收记录](11_ACCEPTANCE_RECORD.md)。

## 免没收标签

- ID：`maledict:vicissitude_confiscation_immune`，item tag。
- common 侧统一 TagKey，建议 `MaledictTags.Items.VICISSITUDE_CONFISCATION_IMMUNE`。每次实际没收前检查 `stack.is(tag)`，命中则留在原槽，不入队列，不触发摘下回调。
- 沿用 COMPLETE/EXTREME 既有入口，只取实际装备 Curio；不扩展到装饰槽、背包或其他难度。
- `data/MaledictItemTags` 生成默认空标签，整合包可用数据包扩充具体物品或其他标签；不擅自默认豁免整类饰品。
- 数据包重载后影响下一次没收，不自动撤销已经发生的没收；已有记录正常返还。
- 目标资源 `data/maledict/tags/items/vicissitude_confiscation_immune.json` 由 runData 生成，禁止直接编辑 src/generated。

数据包示例（示例 ID 必须换成真实物品，不加入默认生成结果）：

```json
{"replace": false, "values": [{"id": "examplemod:protected_curio", "required": false}]}
```

现有生成器把 Incursus Blade/Elegy Bow 加入 `l2hostility:no_seal`，这是既有外部标签适配，不证明用户所指的领取物品来自 L2Hostility，也不要求把本标签与它自动绑定。当前未取得所指模组源码，因此只参考交互模式，不宣称复用了其代码；无需增加依赖。

## 性能与体验比较

| 方案 | 性能 | 玩家操作与缺点 |
| --- | --- | --- |
| 事件触发自动返还（推荐） | 每次重生/死亡/登录只处理该 UUID，成本主要为 N 件饰品的合法装备与同步 | 无额外操作、不占凭证格子；需处理满背包和当前槽位已被占用 |
| 必须右键凭证 | 仍需执行同样的 N 件返还，将工作推迟到右键；另有物品/领取记录管理 | 玩家能选择装备时机，但增加保管、占格与右键步骤，丢失还需补发 |
| 自动返还＋实体凭证兜底 | 兼有两套逻辑 | 对目前需求收益有限，不作为首版推荐 |

普通饰品数量下，自动返还通常更舒服，凭证不天然省算力。复杂装备回调造成尖峰时，两个方案都可能需要分批；先测后决定，不预先建设批处理框架。

## 推荐默认：自动返还，无法交付的继续保管

1. 保留有效攻击逐件返还。玩家死亡时退出本轮目标并登记待返还，重生后 Curios inventory 就绪时恢复；Boss 真死时把剩余饰品全部转入原主人待返还记录，在线玩家立即尝试，离线登录后尝试。
2. 顺序为原合法空槽→其他合法空 Curios 槽→背包；不挤掉现有装备，不跳过 Curios 验证，完整保留附魔及自定义 NBT。
3. 背包不足的部分留在服务端持久记录，不直接丢地上、不删除。向玩家显示剩余件数及“腾出背包空间后会自动返还”。
4. 重生/登录、该玩家背包或 Curios 槽位有效变动时只检查该 UUID；若本版本没有适用的槽位事件，使用仅包含在线待返还 UUID 的低频队列，每 20 tick 检查一次。无人待返还时不扫描，全局不遍历 Boss。
5. 防止返还自身触发槽位事件递归重入：同一玩家一次返还处理中只合并下一次检查，成功交付后再从持久记录扣除相应条目。
6. 跨 Boss 卸载/死亡的记录由世界级索引保管。Boss 与索引之间移交一次，避免同一 stack 两边都可返还；不能把当前战斗尚未解锁的没收物提前放入可领记录。正常保存重载保留余额。
7. 不新增凭证物品。若大量饰品实测有明显单 tick 峰值，再按每玩家每 tick 8 件分批，无需改变玩家交互。

与当前代码相比，需要将批量返还从 Boss 每 tick 检查改成事件/定向待返还队列；满背包从丢地上改为记录保管。不是删除所有必要的重试。

## 凭证备选（只有选择后才实施）

ID 建议 `maledict:curio_return_token`。由主人 UUID 关联世界级记录，不直接把全部饰品 NBT 塞进可复制物品。重生/Boss 死亡后发放；原主人右键一次领取已解锁的全部余额，原槽→合法空槽→背包，不足部分保留。全部交付才消费凭证；旧凭证或重复点击不能复制饰品。

这一分支还需要发放/满背包补发/丢失补领、物品注册、图标、生成模型和中英提示，增加开发与玩家保管负担。当前不把这些计入必须交付，不同时维护两种领取 UI。

## 验收

标签匹配/不匹配/重载、受保护装备未摘下、普通饰品正常没收；逐件返还后再批量返还、死亡/重生/断线、满背包、槽位消失或被占用、多 Boss、正常重启、重复事件无重复物品。测量 1/8 名玩家每人 8/32 件的处理耗时，区分队列查询与第三方装备回调；未实测前不承诺 FPS 或零尖峰。
